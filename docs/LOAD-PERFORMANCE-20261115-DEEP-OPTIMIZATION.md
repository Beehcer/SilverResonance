## 为什么已有缓存仍然慢

缓存已经解决了重复取历史的一部分成本，但原来还有几条等待路径：未显示的品种持续请求；第二窗重复获取初始化信息；未变化的预览重复传输；完整历史重复编码和校验；OSS 慢请求先等超时，再读备用来源。缓存画面显示与完整校验完成也曾混在一起衡量。

本轮分别处理：

1. 只有正在显示的品种持续轮询行情和计划。两个可见窗口均保留更新；后台全品种预热不取消。
2. 两个窗口共享一次初始化续期请求，失败可重试，不改变会话身份。
3. 预览带内容版本。内容没变只返回小响应，不重复传 K 线，也不延长旧行情的新鲜度。
4. 固定坐标引用按品种、坐标基础和引用 ID 精确复用。不同品种不可混用，不截短历史绘图坐标。
5. 未变化的历史前缀复用分块与结构校验；尾部 K 线、历史修正、风险条件和计划权限仍重新核对。
6. OSS 读取超过 800 毫秒时启动服务器备用读取。先通过完整校验的一路获胜，取消另一路；正常快速 OSS 请求不增加备用请求。两路都失败时不写入坏缓存，可重试。
7. 增加接口与浏览器加载耗时记录，区分初始化、历史恢复、完整校验，方便后续定位。

## 浏览器前后对照

方法：同一线上后端、同一台机器、固定前台 Edge 窗口；旧版和新版前端脚本由测试器交付，排除静态文件下载差异。各自预热 20 个品种预览后，按相同顺序切换 20 次。每版本一轮，自然网络环境；这是前端比较，不能代表后端优化的全部收益，也不是统计意义上的速度保证。

| 指标 | 旧版 | 最终新版 | 说明 |
|---|---:|---:|---|
| 缓存画面显示中位数 | 57.5 ms | 57 ms | 已有预览基本立即可见 |
| 缓存画面显示 P95 | 92 ms | 78 ms | 20 次切换样本 |
| 完整校验中位数 | 4,686.5 ms | 3,953 ms | 本轮减少约 15.7% |
| 完整校验 P95 | 5,775 ms | 5,394 ms | 本轮减少约 6.6% |
| 完整校验最慢一次 | 5,813 ms | 5,884 ms | 最坏值没有改善，不作保证 |
| 新增第二窗 | 5,237 ms | 2,694 ms | 单次测量，约减少 48.6% |
| 关闭后重开第二窗 | 4,266 ms | 3,293 ms | 单次测量，约减少 22.8% |

中间版本曾测得碳酸锂完整恢复 9,695 ms，原因是 3 个 OSS 请求超时后顺序备用读取；当时画面 56 ms 已显示。加入提前备用读取后，该品种本轮为 5,394 ms、画面 55 ms。最终轮 237 个下载分块中有 92 个启动备用读取：这是速度与服务器流量的取舍，不能把它说成完全没有额外负担。

初始加载不纳入上述前端脚本对照。第一轮正常公网测试记录首次画面约 5.94 秒、完整可用约 7.81 秒；刷新约 2.06 秒出图、4.27 秒完成校验。首次访问仍受网络、脚本加载、浏览器和缓存是否齐备影响，不能承诺“所有场景零等待”。

早期测试发现新建浏览器测试配置会被扩展欢迎页抢走前台，出现后台节流，相关失败样本保留但不拿来宣称优化收益。对照轮主动维持前台，两版均完成全部步骤且无页面脚本异常。

历史下载并发测试保留 4：24 个交错样本中，并发 4 的中位数 298.15 ms、最大 2,251.4 ms；并发 6 的中位数 280.9 ms、最大 2,980.2 ms。加到 6 没有稳定改善长尾，因此没有为追求数字增加并发。
